TrainingOps · powered by Innotel OnTrak

IT support practice on machines that are already broken.

The IT Support Training Platform powered by Innotel OnTrak stands up a Windows, Server, Office or Linux machine with a real fault injected, opens an in-house ticket against it, hands both to a student in the browser, and grades the fix by reading live system state and the written ticket — then throws the machine away. Every attempt starts from a verified-clean clone, so no two students share the consequences of the last one.

How a session runs

Bare-metal Incus is the only requirement. Everything a student sees is a clone.

1 · Pick a platform

A catalog of manifest entries — not binaries — describes each guest: media source, device profile, resources and how it can be automated. Legacy guests get IDE disks and emulated NICs automatically; there is nothing to hand-configure.

2 · Provision the fastest way available

OnTrak picks the cheapest path the host can actually deliver, and says so: warm pool (instant) → container (~1s) → clone of a broken template (tens of seconds) → launch from a published image → build the image once, as an operator task.

3 · Work the ticket in the browser

Students get an HTML5 console through the gateway, a ticket with a briefing, progressive hints, and a time limit they choose. They can reset as often as they like — a reset is a fresh clone, never an un-break.

4 · Grade live state, not answers

Objective scripts read the machine: does the name resolve, is the service running, is the device enabled. Any correct fix passes, including ones the author did not think of.

5 · Submit and destroy

Practice checks are shown and discarded. Complete & End grades once, records that result, and destroys the machine — results only, no progress tracking.

6 · Keep the lab warm on a schedule

Prewarm windows fill the pool before a class and drain it afterwards, so the first student never watches a boot and idle VMs never hold host memory overnight.

Scenarios, written or generated

Five families, ranked by ticket volume and how cleanly they can be graded.

Network & connectivity

DNS pointed at a dead resolver, proxy traps, static gateways that do not exist. The highest-volume family, and the one with unambiguous evidence.

Boot & performance

Startup bloat, a full system disk. The student has to go looking rather than being handed an error.

Applications & settings

A service disabled, a configuration file corrupted mid-update. The fix is rarely "reinstall".

Hardware & drivers

A device disabled with an error code. Where junior engineers lose the most time.

Security incidents

Simulated persistence, a disabled antivirus, a phishing message to triage. The capstone: it tests process and documentation, not just repair.

Generate your own

Fault primitives compose into new scenarios — ontrak generate one --primitive dns-resolver-trapped --primitive service-disabled — and every generated scenario is validated before it can reach a student.
